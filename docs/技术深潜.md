## 一、一分钟电梯陈述

**做了什么**：一台两轮自平衡小车。STM32F103C8 主控，MPU6050 提供姿态，TB6612 驱动两个带编码器的减速电机，手机 App 通过蓝牙遥控，另配超声波做避障。它能在一定范围内自己保持直立，被推开后自己走回原位，能遥控前进/后退/转向，前方 30 cm 有障碍会拒绝前进。

**技术核心**：三级控制 —— 直立环（PD，内环）保证不倒，速度环（PI，外环）保证不漂移，转向环（PI，闭环角速度）控制朝向。控制环跑在 MPU6050 中断里，固定 112 Hz。

**我的工作**：这套工程基于开源参考实现完成基础功能，我的主要工作是**把它调通、测准、并解决三个实测出来的稳定性问题**，另外新增了几项功能：

1. **实测标定了两个基础常数**（编码器刻度 8197 计数/米、控制周期 8.9 ms）——此前代码用的是推算值，误差可达 1.5~2 倍。
2. **发现并修复了编码器输入滤波未开启的问题**，使直立环可用增益上限从 −122 提升到 −159（+30%）。
3. **重新设计速度环的限幅结构**：P 项与 I 项从"共享一次限幅"改为"各自独立限幅"，解决了轻推无法回位的问题。
4. **把转向环从开环改为闭环角速度控制**，使转向速度不再受电池电压和地面摩擦影响。
5. 补齐了**超声波避障**功能，并解决了"传感器无回波时静默失效"的问题。
6. 搭建了**蓝牙遥测链路**（VOFA+ 实时波形），使全部调参过程都有数据支撑而非凭感觉。

**最值得说的一点**：这个项目里几乎所有结论都有**实测数据**支撑，而且推翻了至少一个此前的错误判断（见第四节"编码器滤波"）。

## 二、系统架构

### 硬件

| 部件 | 型号/接法 | 作用 |
|---|---|---|
| 主控 | STM32F103C8T6，72 MHz | Cortex-M3 |
| 姿态 | MPU6050，软件 I2C（PB3/PB4） | DMP 内部解算四元数 → 倾角 |
| 电机驱动 | TB6612 | TIM1 CH1/CH4 出 PWM，PB12–15 出方向 |
| 电机 | 25GA370，编码器 11 PPR，减速比 20.4 | 轮径 65 mm |
| 编码器接口 | TIM2（PA0/PA1）、TIM4（PB6/PB7） | TI12 模式，双边沿计数 |
| 蓝牙 | JDY-31，USART3，9600 波特 | 收遥控 + 发遥测 |
| 超声波 | HC-SR04，PA3 触发、PA2 回波 | 避障测距 |
| 显示 | OLED（SSD1306），硬件 I2C1 | 本地调试显示 |

### 实测基础常数（面试重点：这些是测出来的，不是算出来的）

| 常数 | 值 | 怎么测的 |
|---|---|---|
| 控制周期 | **8.9 ms（112 Hz）** | 用 `HAL_GetTick()` 对 100 次中断取平均，并实时上报到上位机 |
| 编码器刻度 | **8197 计数/米** | 用手把车推**恰好 1.00 米**，读无饱和累加器的变化量 |
| 电机突破 PWM | **约 350 / 7200 = 4.86%** | 空载逐步加 PWM，观察车轮起转点 |
| 机械中心角 | **2.20°** | 跑起来后取倾角平均值（原理见下） |

### 控制架构

```
                 编码器 ──►┌────────────┐
   目标速度 0 ────────────►│ 速度环 PI  │── Velocity_out（度）
                           └────────────┘        │
                                                 ▼ 加到角度目标
         Med_Angle(2.20°) ─────────────►┌────────────┐
                    倾角 roll ──────────►│ 直立环 PD  │── Vertical_out（PWM）
                  角速度 gyrox ─────────►└────────────┘        │
                                                               ▼
                                          MOTO1 = V − Turn
                                          MOTO2 = V + Turn
                                                               ▲
   遥控目标转速 ──►┌────────────┐                               │
                   │ 转向环 PI  │── Turn_out（差速 PWM）────────┘
   陀螺仪 gyroz ──►│            │
                   └────────────┘
```

**三个环的分工**：

| 环 | 类型 | 输入 | 输出 | 解决什么问题 |
|---|---|---|---|---|
| 直立环 | PD | 倾角、角速度 | PWM | 车不倒（**唯一不可省**） |
| 速度环 | PI | 编码器速度 | 角度偏移 | 车不漂走，被推后走回原位 |
| 转向环 | PI | 陀螺仪偏航角速度 | 差速 PWM | 遥控转向、抑制自转 |

## 三、时间线：节拍与并发

**控制节拍来自硬件中断，不来自主循环**：

```
MPU6050 的 DMP 每算好一组姿态数据 → 拉低 INT 引脚（PB5）
        ↓
EXTI9_5_IRQHandler
        ↓
Control()  ← 完整跑完一次采样 + 三个环 + 输出，周期 8.9 ms
```

`main()` 的 `while(1)` 只做两件不紧急的事：

- 每 5 个控制周期发一帧遥测到电脑（VOFA+ 显示波形）
- 每 200 ms 刷新一次 OLED

**为什么这个设计重要**：串口发送一个 24 字节帧在 9600 波特下要**阻塞约 25 ms**，比一个控制周期还长。如果控制逻辑放在主循环里，控制频率会被串口拖到不可预测，车必然不稳定。放在中断里之后，**控制周期的抖动与主循环完全解耦**，实测稳定在 8.9 ms。

## 四、三个有技术含量的实测问题及解决过程（面试主要谈资）

### 问题 1：编码器输入滤波未开启，白白吃掉了 30% 的增益

**现象**：直立环增益提到 −135 以上就开始明显抖动，−160 时剧烈抖动后翻倒。初步判断是"环路相位裕度已经到极限"。

**排查**：检查 `tim.c` 发现 TIM2/TIM4 的编码器输入滤波 `IC1Filter = 0`、`IC2Filter = 0`——**完全没开**。而编码器工作在 TI12 模式，两个通道的每个边沿都计数，同时电机线就在编码器线旁边跑着 10 kHz 的 PWM。

**定量分析**：一个毛刺 = 一个虚假计数。经过速度环折算，1 个假计数相当于 **0.55° 的目标角偏移**，在直立环增益下就是 **67 的 PWM 输出抖动**。这个噪声直接喂进了速度环的 P 项。

**解决**：把滤波设为 15（在 2.25 MHz 下采 8 次，滤掉短于约 3.6 µs 的脉冲）。真实编码器脉冲即使车速到 2 m/s 仍有约 227 µs 宽，**余量 60 倍**，不会误杀真脉冲。

**结果**：直立环可用增益从 **−122 提升到 −159（+30%）**，稳态抖动明显减小，角度死区从 1.02° 降到 0.79°，位置盲区从 2.9 cm 降到 2.4 cm。

**这个案例的价值**：它**推翻了原来的结论**。此前判断"环路已到相位裕度上限"只对了一半——真正吃掉裕度的不是传感器的延迟，而是编码器毛刺喂进来的噪声。**先堵上游噪声，再谈调参**，这是本题最大的方法论收获。

### 问题 2：限幅结构错误，导致"轻推回不来"

**现象**：轻推小车后它不回来，或者回来时震荡次数很多；大力推反而更容易冲过头。

**排查**：原来的写法是**对 P 项和 I 项之和对一次限幅**：

```c
temp = P项 + 积分项;
if (temp > 15) temp = 15;   // 两道限幅抢同一个额度
```

**机理**：积分项上限是 12°，总和上限 15°，那么积分项一旦攒满 12°，**留给 P 项的空间只剩 3°**。而 P 项恰恰是"速度阻尼"，也就是**刹车能力**。结果是车在最需要刹车的时候失去了刹车——轻推回不来、越晃越远。

**解决**：两项各自独立限幅，`VEL_P_LIMIT = 18`、`VEL_INT_LIMIT = 15`，直接相加，最坏 33°（摔倒保护线是 45°）。

**补充认识**：`VEL_INT_LIMIT` 不只是一个安全上限，它还决定了"线性范围"：

```
可推距离 = VEL_INT_LIMIT / (|Ki| × 8197)  米
```

积分项一旦饱和，位置环就等于开环，车退化成**开关控制（bang-bang）**，必然过冲。实测：`Ki=−0.006 / 限幅 8°` 时线性范围只有 15 cm，一次普通手推就饱和；改成 `Ki=−0.004 / 限幅 15°` 后是 46 cm，覆盖了车有可能恢复的任何推力。

### 问题 3：外环不能加滞后——一次失败的实验

**假设**：速度环误差抖动较大，加大低通滤波（时间常数从 25 ms 提到 84 ms）应该能让输出更平滑。

**结果**：车从"能守位"变成**前后徘徊、幅度越来越大直到摔倒**。

**原因**：速度环是外环，它的任何滞后都直接侵蚀相位裕度，导致低频自激。

**结论**：外环的一切都必须保持"快"。这条规律在项目里出现过两次：另一次是速度环 `Kp` 调到 −1.0 量级时，穿越频率挤进内环带宽，车出现约 1 Hz 自激振荡；降到 −0.58 后晃动幅度缩小约 5 倍。

**文档化**：这个失败的实验和它的机理都记录在代码注释里，避免后来者（包括三个月后的自己）重复踩坑。

### 另外两项功能性改进

**转向环从开环改为闭环**：

- 原方案：`Turn_out = Kp × 目标转速 + Kd × gyroz`，**从不比较指令与实测**，所以实际转向速度随电池电压和地面摩擦变化，而且"转 100 度/秒"这种指令根本无法表达。
- 新方案：对**偏航角速度做 PI 闭环**。指令和实测同为陀螺仪原始值（16.4 LSB/dps），可以相减。附带好处：目标转速为 0 时误差就是 −gyroz，**这个环自动就在阻尼任何自转**，不需要额外的"空闲阻尼"逻辑。
- 积分项的必要性：电机有死区，纯 P 环维持不了很小的转速；陀螺仪原始值也有零漂。积分项把这两个问题一起吸收。

**超声波避障 + 失效检测**：

- 原状：超声波接好了但**从未被调用**，`distance` 永远是 0——功能等于不存在。
- 修改：在控制周期里定时触发（约 107 ms 一次）。
- **隐蔽的坑**：没收到回波时中断根本不执行，`distance` 会一直保留上一个值，看起来完全正常，其实传感器已经"瞎了"。解决办法是盯着**回波脉冲宽度** `count`——只有真的收到回波它才会变化。发射前记下 `count`，等约 53 ms 后再看它有没有变；没变就判定读数过期，**跳过避障判断**（此时车完全听遥控指令）。

## 五、面试官可能追问的问题（附参考回答）

### A 级：基础必须答得出

**A1. 平衡车为什么不会倒？**

它靠**移动底座**来平衡，而不是靠额外的力矩。车往前倾时，控制器驱动轮子往前加速，轮子跑到车身重心下方，车体就被"接住"了。所以直立环本质上控制的是**轮子的加速度**，而不是位置。倾角 θ 与所需加速度 a 的关系是 `a ≈ g·tan(θ)`，这正是双轮倒立摆的欠驱动特性——只有 1 个驱动自由度（前进/后退），却要同时控制倾角和位置两个量。

**A2. 为什么需要速度环？只有直立环不行吗？**

不行。只有直立环时，它只保证"角度对"，不关心"在哪里"。任何一点角度偏差都会积分成恒定的加速度，车就慢慢飘走了——表现为"能立住，但推一下就一直滑走"。

速度环的做法是**不直接驱动电机，而是去修改直立环的目标角度**。车被推向前 → 角度目标变大 → 车体被要求前倾 → 前倾产生向前加速度 → 而这个"向前"恰好抵消刚才被推出去的位移。

**A3. 控制周期是多少？怎么确定的？**

实测 8.9 ms（约 112 Hz）。不是设定的，而是 MPU6050 的 DMP 输出速率（配置为 100 Hz）经过实际测量得到的。代码里用 `HAL_GetTick()` 对 100 次中断取平均来消除 1 ms 计时精度的影响，并把结果实时上报到上位机。

**测准这一步是必需的**：如果代码写死 0.01 s，而中断实际只有 50 Hz，那么算法以为转过的角度只有真实值的一半，车要歪好几厘米才"感觉到"倾斜，然后过度修正——表现就是"反应迟钝但一修就过头"。

**A4. 什么是电机死区？为什么它对平衡车特别致命？**

PWM 低于某个值时电机完全转不动（本车实测约 350/7200 = 4.86%）。致命之处在于这个死区会被**整条控制链放大**：

```
电机死区 350 PWM
  ↓ 补偿后残余 125 PWM
  ↓ ÷ Kp = 159 PWM/度
角度死区 0.79°
  ↓ ÷ (Ki × 8197)
位置盲区 2.4 cm
```

也就是说，在控制环真正做出反应之前，车已经"盲目"走了约 2.4 厘米。这就是"轻推没反应、再推一点就猛窜"的根源。

**解决办法是在输出端做连续补偿**：

```c
out = p + D × tanh(p / S)
```

用 `tanh` 而不是简单地把 `0~MAX` 拉伸到 `D~MAX`，是因为后者在指令穿越零点时会**跳变 2D**，而控制环在零点附近来回穿越极其频繁，这个跳变会被感知为抖动。`tanh` 形式过零点平滑，同时仍能补回全部偏移。

**A5. 为什么用 MPU6050 的 DMP 而不是自己算姿态？**

DMP 是 MPU6050 内部的协处理器，直接输出四元数/欧拉角，省掉了主控的运算量和一套姿态解算代码。代价是：

- 输出有一定延迟（DMP 内部 FIFO 和滤波带来），这是控制环相位裕度的消耗项之一；
- 输出速率受限（这里配成 100 Hz，实测出 112 Hz 的控制周期）；
- 无法灵活调整滤波参数。

项目里也试过自己写互补滤波（用加速度计做慢速绝对参考、陀螺仪积分做快速响应），但**实测没有净收益**：符号和零点难以对齐，两条曲线会发散。最终结论是 **DMP 的延迟不是主要瓶颈，电机死区才是**，所以关闭了互补滤波，直接用 DMP 角度。

### B 级：区分"调过参"和"真懂"

**B1. 三个环的频率为什么必须拉开？**

这是串级控制的基本约束：内环必须比外环快得多，否则外环的调节动作会被内环"看见"成扰动，两者互相激励产生振荡。

项目里的实测证据：速度环 `Kp` 调到 −1.0 量级时，外环穿越频率约 2.13 Hz，挤进了内环带宽，车出现约 1 Hz 的自激振荡；降到 −0.58 后穿越频率约 1.15 Hz，晃动幅度缩小 5 倍。

**B2. 内外环的角色由什么决定？**

由物理动力学的快慢决定。车"倒下去"的时间常数远小于车"滑走"的时间常数，所以直立环必须在内、速度环必须在外。

**B3. 积分限幅为什么能决定"线性范围"？**

因为积分项累加的是速度误差，物理意义是**位移**。积分输出 = `Ki × 位移`。当 `|Ki × 位移|` 达到限幅值时，积分项就不再增长了——位置反馈失效，车退化成开关控制。

```
线性范围 = 限幅值 / (|Ki| × 8197)  米
```

所以这个限幅值的选择是一个**设计权衡**：设小了线性范围不够（普通手推就饱和），设大了最坏情况下的角度偏移过大（可能触及摔倒保护线）。最终 18 + 15 = 33°，低于 45° 的保护线。

**B4. 转向环为什么必须是闭环？**

开环形式 `Kp × 目标 + Kd × 实测` 有两个硬伤：

1. **从不比较指令和实际值**，所以实际转向速度会随电池电压下降、地面摩擦变化而改变——同一个指令在不同电量下转向快慢不同。
2. 目标值是个"任意刻度"（原来是 150），**没有物理意义**，"转 100 度/秒"这种需求无法表达。

改成对偏航角速度的 PI 闭环后，指令和反馈都是同一物理量（陀螺仪原始值，16.4 LSB/dps），可以直接相减，转向速度就成了可复现的物理量。

**B5. 为什么 P 项和 I 项必须独立限幅？**

P 项是**阻尼**（刹车能力），I 项是**刚度**（回位能力）。如果对两者之和对一次限幅，积分项攒满后就会挤占 P 项的空间，**阻尼/刚度比塌陷**。

实测数据：

| 推开距离 | P 项（上限 12°） | I 项 | 阻尼/刚度比 |
|---|---|---|---|
| 15 cm | 11.6° | 4.9° | 2.36 ✓ |
| 25 cm | **12.0°（已削平）** | 8.2° | 1.46 ✗ |
| 40 cm | **12.0°（已削平）** | 13.1° | 0.91 ✗ |

可以看到推力越大，P 项越早削平、而 I 项还在涨，阻尼比越来越低，回程必然过冲。修法是把 P 项上限从 12° 抬到 18°，并保持两项独立。

**这个修改的一个好性质**：在线性区内（`|P项| < 12°`）代码行为**逐位不变**，所以它是稳定性中性的——只改善大信号行为，不改小信号。

### C 级：加分项 / 方法论

**C1. 你怎么知道一个结论是对的？**

只信实测数据。举例：判断"编码器刻度是 8197 还是 8790"不能靠推算（11 PPR × 4 倍频 × 20.4 减速比 / π×0.065），因为编码器线数如果不是 11 而是 13，推算值就错 1.5~2 倍，而速度环的位置增益、死区、稳定性全都依赖这个常数——**足以把"刚好稳定"变成"发散"**。

做法是：推车恰好 1.00 米，读一个**不受限幅的**累加器。这里有个细节：控制用的积分器被限幅了，折算下来只能记录约 0.43 米，推 1 米会提前饱和导致测量失真，所以专门维护了一个无饱和的副本用于标定。

**C2. 遇到"车抖动"怎么定位？**

按"先上游、后下游"的顺序排查，因为**控制环会把上游的任何噪声放大**：

1. **机械**：轮子是否偏心、螺丝是否松
2. **传感器噪声**：编码器滤波开了吗？（本项目的关键发现）陀螺仪读数是否干净
3. **控制参数**：先降增益看是否消失，确认是增益问题还是噪声问题
4. **采样与节拍**：控制周期是否稳定、是否有丢帧

本项目最大的教训就是：一开始把抖动归因于"相位裕度到极限"，实际是第 2 步的传感器噪声。**先堵上游，再调下游。**

**C3. 为什么不直接在代码里写死控制周期 0.01 s？**

因为这个值只在你确信中断频率时才对。实测是 8.9 ms 而不是 10 ms，误差 12%——对本项目用到的互补滤波积分来说，这个误差会直接变成角度计算的系统偏差。而且中断频率会随 DMP 配置、I2C 总线负载变化，所以**测量比假设更可靠**。

**C4. 遥测为什么值得花时间做？**

因为调参的瓶颈不是"不会调"，而是"看不见"。这个项目用蓝牙把 7 个通道实时传到电脑上的 VOFA+ 画波形：

```
roll(倾角) | gyrox(角速度) | 直立环输出 | 速度环输出 |
轮速 | 摔倒标志 | 实测控制周期
```

有了波形之后：

- "车在抖"变成"抖动频率 12 Hz、幅度 0.8°"，可以直接判断是噪声还是自激；
- 每个参数改动的效果可以量化对比，而不是凭感觉；
- **实测控制周期这一路是自查工具**——它一眼就能看出控制频率是否正常，排除了大量误判。

**C5. 这个项目的局限在哪？（诚实回答，加分项）**

1. **电机死区和环路增益裕度存在物理冲突**。要把死区压得更小，就需要更大的补偿斜率（= 额外环路增益），而本环路的增益裕度已经用光。实测数据：补偿 `D=260/S=100`（斜率 3.6）时车稳定但轻推被死区吃掉；改成 `D=360/S=70`（斜率 6.1）后抖动加剧、1~2 cm 的轻推就会发散。**没有可用的中间窗口**——要突破必须改硬件（低齿槽转矩电机、电流环驱动、或磁编码器）。
2. **蓝牙协议本身没有链路保护**。手机 App 每次按键只发一个字节、按住不重复发送，所以"前进中收不到数据"是正常状态，任何掉线超时都会在正常行驶时误停车。**正确的修法**是把蓝牙模块的 STATE 引脚接到 GPIO 上，但这个模块没有引出该引脚。
3. **只做到了速度控制，没做位置/路径规划**。
4. 供电是电池直供，**电压下降会影响实际转向速度**（转向环闭环缓解了这个问题，但直立环的 PWM 到力矩转换仍然受电压影响）。

### 部分问题的"陷阱提示"

- **第 4 题**：很多人会答"因为速度环要控制速度"——这只说了一半。关键是**速度环的输出是"角度偏移"而不是 PWM**，它通过"故意让车倾斜"来产生加速度。要讲清这个间接作用机制。
- **第 9 题**：只说"分开限幅更安全"是不够的，要讲**阻尼/刚度比塌陷**这个机理，并给出实测数据（15 cm 时比值 2.36、40 cm 时降到 0.91）。
- **第 14 题**：这是在问**你是否敢于推翻自己的结论**。诚实回答"我一开始判断错了，以为是相位裕度问题，后来通过检查寄存器配置发现是编码器噪声"是加分项。
- **第 20 题**：考点是**工具链差异的工程敏感度**。至少要能说出：ARMCC 标准库默认支持 `printf` 浮点而 GCC + newlib-nano 需要显式链接 `-u _printf_float`（否则 `%.2f` 输出为空——这个现象很隐蔽，编译完全不报错）。
